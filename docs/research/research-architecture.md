# Исследование

## Последняя проверка: подпись завершена, qualification остановилась, 2026-10-04

Владелец запустил read-only обновление. Оба codesign и strict verify завершились, сохранён signature-ready.json; новый fingerprint совпадает с qualification-started.json и фактическими файлами. Отдельная public CodeSigning/revocation оценка вернула -67635 с причиной «Не удалось проверить аннулирование» до OFF. Это не подтверждение отзыва сертификата. Владелец не видел Keychain prompt; причина отсутствия запроса не установлена, результат подписи от него не зависит. Повтор wrapper отказал на существующем update-started.json до дальнейших действий.

Две новые strict verify в обычном пользовательском окружении прошли. В sandbox те же проверки вернули CSSMERR_TP_NOT_TRUSTED; этот результат не переносится на owner окружение. Сохранены все 12 файлов остановленного пакета; установленный старый fingerprint неизменен, runtime/staging/backup отсутствуют. Removal/replacement/registration markers не созданы. Аппаратных записей нет. [Markers, хеши и проверка подписей](evidence/owner-profile-update-qualification-stop.json). Следующий шаг — подготовить отдельное продолжение из точных подписанных файлов и завершить public qualification разработчиком до следующего owner действия; повтор подписи и пересборка не нужны.

Продолжение подготовлено: один public qualify нового `.build/owner-profile-update-resume` завершился 0 с positiveRevocation=true на тех же signed hashes. Причина различия с owner отказом не установлена; trust/revocation policy сохранена. Новый seal создан до owner действий, hardware review отсутствует. Импорт связывает все source файлы и signature/qualification markers, запрещает lifecycle-started source и перенос read-only source в аппаратный пакет. Unsealed продолжение отказывает до OFF, подпись импортированного пакета запрещена. CLI/model, семь source mutations, copy race и прежний owner regression прошли; фактический no-TTY отказал до marker. Исходные 12 и прежние 15+7+8 файлов, installed hashes и отсутствующие runtime/staging/backup сохранены. Следующий owner шаг — одна команда по [полному продолжению](../owner-helper-update-resume.md), начиная с OFF, без подписи/повторной qualification. Actual replacement/root XPC остаются непроверенными. [Подготовка, seal и сохранность](evidence/owner-profile-update-resume-package.json).

## Последняя проверка: job загружен, ОС изменилась, 2026-10-04

Один owner off/on завершился: административный print вернул 0, job submitted by SMAppService, runs=0 до XPC-запроса. Child BTM generation выросла 903→905, user parent 18→20; parent pending authorization сохранился. Значит этот текст не препятствует фактически загруженному job в текущем состоянии. Exact owner/installed файлы неизменны. Единственный developer verify-installed-helper получил enabled/deadline, helperVerified=false; launchd затем самостоятельно повторял spawn, каждый helper завершался exit 78. Startup log подтверждает отказ **stage=runtime, error=untrustedSignature**, после проверки identity; runtime root отсутствует.

Read-only `sw_vers` теперь сообщает **27.0.1 (26A434)**, модель прежняя Mac15,7. Immutable candidate остаётся **27.0.0 (26A428)**. `HardwareRecoveryIdentity.currentBoot` объединяет root/profile/signature в один guard с untrustedSignature; несовпадение профиля объясняет этот runtime отказ. Это ошибка диагностики и связи запуска daemon с экспериментальным профилем. Старый hardware plan неприменим к новой ОС; receipt/start/SMC не выполнялись. Следующий шаг — исправить запуск диагностического helper на неподтверждённом профиле, сохранив запрет аппаратного runtime, затем подготовить полный read-only сеанс обновления. [Точные наблюдения](evidence/owner-system-approval-result.json).

Исправление собрано с ad hoc подписью: неподтверждённый профиль сохраняет diagnostic listener и явно закрывает preparation/start, hardware authority/recovery не инициализируются. Candidate 26A428, guards подписи/root/receipt/ledger не расширены. 104 Swift-теста прошли; три unsupported XPC профиля и четыре прежних model runtime пути прошли. Read-only update модель проверила три успеха и двенадцать отказов, включая OS change до marker, signing/qualification, OFF/ON, hash/runtime/removal/register/peer и запрет повторов. Новое обычное read-only приложение на 26A434 прочитало два вентилятора с прежними диапазонами/mode=3; CPU/GPU/SSD оставлены n/a, Tf26 не атрибутирован. [Probe](evidence/macos-26A434-read-only.txt).

Подготовлен unstarted `.build/owner-profile-update`: frozen plan/script, ad hoc fingerprints и точный pin прежней installed копии. Hardware candidate/review/receipt не создаются; hardware и отдельные lifecycle команды закрыты, одна owner-команда выполняет все фазы по [полному read-only плану](../owner-helper-update.md). Actual no-TTY вызов отказал до marker/ключа/sudo. Сохранены 15 owner, 7 прежних diagnostic и 8 system-cycle файлов; installed hashes неизменны. Следующий шаг требует owner Terminal/keychain/Settings/sudo, фактический новый signed root peer пока не проверен. [Подготовка и точные хеши](evidence/owner-profile-update-package.json).

Владелец ответил «да» на вопрос о появлении и подтверждении последнего административного запроса. Это owner report, не подтверждение effective OS authorization: новый native read-only status остаётся notRegistered, job отсутствует (113), runtime root — ENOENT, installed signed/root-owned hashes прежние. Подготовлен новый installed continuation без file installation/unregister: exact source/installed admission до/после копирования, новый full review, один register и ready в owner-only setup. Existing runtime/job/alias/unreadable state/changed hash блокируют admission до запуска app; pending/отказ не вызывают ready. Модель и full Swift review gate прошли. Strict verify и одна public qualification exact signed файлов прошли; новый review запечатан. Fresh установка владельцем прошла: installed fingerprint совпадает с seal, native signed/root-owned/location gates положительны. Первый wrapper исходно увидел requiresApproval. Узкий system log подтвердил успешный unregister (status 2→0), затем через 70 мс register error=1 с `Job is not allowed to bootstrap`; actual status остался notRegistered. Причина effective authorization и факт admin prompt не доказаны. [Apple DTS](https://developer.apple.com/forums/thread/783539) описывает race немедленного unregister/register даже с completion; перенос на этот Mac — гипотеза. Исправлен fresh wrapper: existing requiresApproval сохраняется без lifecycle mutations, ошибка называет action; модель проверяет post-register отказы и запрет повторов. Все 16 файлов stopped sealed пакета сохраняются без изменений; native executable не пересобирались, public qualification не повторялась, hardware gate закрыт. Подготовлен новый полный [сеанс чистой установки](../owner-session.md): explicit signed-source `--fresh-install` сохраняет provenance без operative previous pin; установка требует пустых путей/runtime/job и one-shot marker; регистрация допускает один guarded unregister только для unstarted requiresApproval, затем register, без глобального reset. Прежний пакет целиком сохранён (15 hash), signed source не изменён (11 hash). Те же signed executable прошли strict verify и одну public qualification; новый полный review запечатан. Владелец включил фоновую активность, но `ready` опять вернул `requiresApproval/serviceNotEnabled`. Read-only Settings AX подтвердил `background-switch-Ventilator=on`; actual native status повторил отказ на неизменных signed хешах. В BTM helper имеет `enabled, allowed`, но parent app для UID -2 — `disabled, disallowed, pending authorization`, для UID 501 — `disabled, allowed, pending authorization`; URL обоих parent записей — текущий `/Applications/Ventilator.app`. Job отсутствует, runtime root — lstat ENOENT. Включённый переключатель сам по себе не подтверждает effective daemon authorization. [Apple DTS](https://developer.apple.com/forums/thread/802443) показывает отдельное Allow в Background Items Added с административным подтверждением; этот пример проверен на macOS 15.6.1, а не 27. Пропущенное/незавершённое подтверждение — гипотеза, причина рассогласования не доказана; наличие notification/auth sheet здесь не проверено. У владельца запрошен факт запроса пароля/Touch ID. Повторы регистрации/ready, resetbtm и manual bootstrap не выполнялись; sealed пакет сохранён, аппаратный опыт не начинался. [Точные факты и границы](evidence/owner-system-authorization-pending.json).

Последний вывод владельца после новой регистрации: `register` возвращает `requiresApproval/serviceNotEnabled` без STOP, затем `ready` отказывает с тем же статусом и exit 78. Хеши совпадают с новой подписанной сборкой. Это ожидание системного одобрения: код проверяет `enabled` до XPC, а wrapper импортирует protected review только после успешной проверки helper. Следующий шаг — включить Ventilator в «Системные настройки → Основные → Объекты входа и расширения → Фоновая активность приложений», подтвердить системный запрос и только после этого выполнить `ready`. Положение переключателя не проверялось; повторная подпись/замена/регистрация не требуется. Sealed пакет не менялся, новый root XPC остаётся непроверенным. [Вывод и границы](evidence/owner-helper-update-completed.json), [раздел настроек Apple](https://support.apple.com/ru-ru/guide/mac-help/mtusr003/mac).

Продолжение после PR #14: новая signed сборка уже установлена root-owned; её три digest совпадают с seal и replacement-completed, backup содержит точный предыдущий pin, staging отсутствует. Повтор replace-installed остановился, потому что новая установленная сборка уже отличается от прежнего pin; новых файловых операций не было. Native app status подтвердил trustedBundle/rootOwned/installedLocation, registration=requiresApproval, helperVerified=false/serviceNotEnabled. Весь runtime root отсутствует; protected review/approval/аппаратный опыт ещё не начинались. Sealed PLAN/script/review не меняются: следующий предусмотренный шаг — unregister/register, системное разрешение и ready (шаг 3). [Подтверждение](evidence/owner-helper-update-completed.json).

Продолжение после PR #13: владелец подписал исправленные executable; sign остановился на `-67635`/«Не удалось проверить аннулирование». Strict verify обоих файлов и одна отдельная public qualification exact тех же файлов прошли; файлы не изменены, private key не использован. Причина отказа не установлена. Наша обязательная [positive-response policy](https://developer.apple.com/documentation/security/ksecrevocationrequirepositiveresponse) отвергает отсутствие подтверждённого ответа (семантика также проверена в macOS 27 SDK SecPolicy.h); сообщение само по себе не доказывает отзыв. Разделены завершение sign и qualify; check показывает стадии отдельно. Signed-source import и полное новое review позволяют продолжить без пересборки/повторной подписи. Hardware gate/политика trust не ослаблены. [Свидетельство](evidence/owner-signing-stages.json).

После системного одобрения actual registration=enabled, signed/root-owned/installed gates прошли, но root XPC дал deadline. Launchd успешно spawn-ил helper, а тот завершился exit 78 примерно через 10 мс; это не подтверждает гипотезу медленного cold start. Старый код вычислял bundle/child paths из argv[0]. На установленном signed приложении с overridden relative argv воспроизведён invalidLayout. Actual root argv получить не удалось, поэтому причина именно этого daemon отказа остаётся гипотезой. [Факты и границы](evidence/owner-ready-deadline.json).

Исправление использует `_NSGetExecutablePath` для загруженного executable и сохраняет прежнюю проверку aliases/signatures/ownership. [Apple dyld](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/dyld.3.html) допускает symlink в возвращённом пути; ранний realpath не применяется. Проверены relative/foreign/opaque argv[0] на настоящих app/helper subprocess. Startup log фиксирует этап identity/runtime/listener. Увеличение срока handshake не требуется для этого воспроизведённого дефекта.

Runtime root отсутствовал, ready остановился до защищённого review/approval/SMC. Для новой сборки подготовлен полный disabled update: owner выключает фоновое разрешение; wrapper требует точный старый pin, native gates, non-enabled status, отсутствие всего root state/активного PID и сохраняет отдельный backup. Лишь остаточный точный inactive job допускает один bootout; после staging job или смена hash запрещают оба mv. Узкий unregister требует requiresApproval и lstat ENOENT всего runtime root; enabled путь по-прежнему требует живой peer без pending. Framework error 1 нормализуется только с actual requiresApproval; диагностическое сообщение сохраняется. Эти новые ветки проверены на модели, реальная новая установка/root XPC не выполнены. Прежний sealed пакет сохраняется целиком; из-за изменения executable требуется новая подпись по [полному плану](../owner-session.md). Mac остаётся read-only, physicalAutoVerified=false.

## Область и статус

Основа — [задание владельца](evidence/owner-brief.txt), приложенное к запросу 2026-09-30. Репозиторий на момент первоначального исследования не содержал приложения. M1 теперь содержит работающий прототип наблюдения; дальнейшие решения и проверки ниже явно отделены от сделанного. **Ручное управление вентиляторами на данном Mac не доказано; запись в SMC не выполнялась.** Это исследование не служит разрешением на аппаратный эксперимент.

Продукт — одно нативное приложение macOS в одном репозитории. Исследование хранится постоянно; [feature](../features/feature-observation.md), [screen](../screens/screen-overview.md) и [service](../services/ventilator-app.md) документы описывают нынешнюю реализацию. Отдельного HTTP API и серверной части в задании нет; XPC здесь внутренний IPC, а не слой API для сетевых маршрутов.

### Внешнее эмпирическое свидетельство, не проверенное на этом Mac

Автор [MacFanControl](https://github.com/raminsharifi/MacFanControl) сообщает об успешном контроле `Mac15,7` на **macOS 26** и описывает ключи `FNum`, `F*Ac`, `F*Mn`, `F*Mx`, `F*Tg`, `F*Md`, `Ftst`, а также многосекундную передачу управления от `thermalmonitord`. [Исходный модуль чтения SMC](https://github.com/raminsharifi/MacFanControl/blob/main/src/smc.rs) подтверждает, что проект использует IOKit и самостоятельно проверяет тип данных ключа. Это полезная отправная точка для реализации, но не доказательство, что последовательность записи работает и безопасно восстанавливается на macOS 27.

[Stats](https://github.com/exelban/stats) предупреждает, что набор температурных ключей меняется с поколением SoC, а отображение некоторых сенсоров на CPU/GPU неточно; его управление вентиляторами не поддерживается активно. Следовательно, имя датчика нельзя вывести только по префиксу ключа или по правдоподобной температуре. Документированный Apple [IOATASMARTInterface](https://developer.apple.com/documentation/iokit/ioatasmartinterface) относится к ATA SMART; применимость к встроенному Apple NVMe SSD из этого источника не следует.

[iSMC](https://github.com/dkorunic/iSMC) описывает HID sensor hub как путь чтения температур на Apple Silicon и публикует кандидатные ключи M3 для CPU/GPU/SSD. Это внешняя кандидатная карта; локальный HID-путь теперь проверен, NAND атрибутирован, а карта CPU/GPU пока не подтверждена. См. [исследование температур](research-temperatures.md). Реализация iSMC распространяется под GPL-3.0, поэтому её код не переносится в этот проект.

| Решение | Причина и отклонённая альтернатива |

| Низкоуровневый протокол SMC изолировать в небольшой модуль с фиксированными операциями, проверкой размера/типа ключа и машинно проверяемым профилем модели+сборки ОС. | Протокол ключей эмпирический и может меняться. Универсальный «запиши произвольные 4 байта» опасен. Пробник исследовательский; продуктовый модуль должен иметь собственную проверку и тесты. |

M1 реализовал первые три решения в `Sources/CSMCRead/`, `Sources/VentilatorCore/` и `Sources/Ventilator/`. Низкоуровневый модуль содержит только команды метаданных, перечисления имён и чтения; запись командой 6 отсутствует. Пункт о помощнике остаётся планом M2. Владелец подтвердил работу `NSStatusItem` на живом экране 2026-09-30; [протокол](evidence/m1-product-probe.txt).

Отдельное [исследование температур](research-temperatures.md) на той же машине обнаружило 252 SMC-ключа `T…` и 46 HID-сервисов температуры; 45 HID-сервисов вернули значения. `NAND CH0 temp` предоставляется `AppleEmbeddedNVMeTemperatureSensor` под `AppleANS3CGv2Controller`: физический источник накопителя подтверждён и включён в продукт через `CHIDTemperature`. Короткие CPU/Metal-нагрузки с 45 снимками оставались при номинальном thermal pressure. CPU/GPU-атрибуция PMU и SMC пока не подтверждена; эти два показания остаются неизвестными. Девять тестов прошли, продуктовый `--probe` прочитал NAND; [протокол](evidence/temperature-product-probe.txt).

Начальная часть M2 реализована как [чистая проверка снимков](../../Sources/VentilatorCore/ExperimentVerification.swift): точная модель/сборка, свежие значения, два вентилятора, диапазоны и умеренная кандидатная цель 2500 RPM. Подставные тесты требуют независимых чтений режима, цели и роста фактических RPM, затем трёх разнесённых по времени чтений кода Auto. Это **только часть доказательства**: код `3`, состояние `Ftst` и физический возврат системного управления остаются непроверенными. Проверка не вызывается из UI и не содержит записи.

Следующий шаг M2 реализован как [симуляция сеанса](../features/feature-control-simulation.md) и [прототип helper](../services/ventilator-helper.md): ограниченный RPC, server-side binding соединения, lease 10 с, heartbeat 2 с, атомарный приватный файловый маркер и восстановление по трём чтениям. XPC coordinator теперь передаёт операции отдельному процессу через приватные pipe; worker единолично владеет моделью, журналом и таймером. Пройден настоящий anonymous XPC, SIGKILL симулятора с перезапуском, SIGKILL помощника с продолжающим работать worker (Auto-коды за 2,34 с), SIGSTOP помощника (4,32 с), SIGTERM worker и отказ Auto с сохранением маркера; [протокол](evidence/control-dry-run.txt). 27 тестов прошли. В fixed устранён дефект неполного baseline; изменение min/max в активном сеансе также вызывает Auto.

`IORegisterForSystemPower` успешно зарегистрировал observer в локальном непривилегированном dry-run. Подставное событие вызывает восстановление до acknowledgement; **доставка настоящего сна не проверена**, Mac не усыплялся. Использован публичный API из [Apple QA1340](https://developer.apple.com/library/archive/qa/qa1340/_index.html) и заголовков установленного SDK. Уведомление разрешает сон после синхронной операции модели и не доказывает, что аппаратный транспорт успеет завершиться. Авария самого worker и блокирующий аппаратный I/O этой проверкой не покрыты.

Helper собран в bundle, но не зарегистрирован и не связан с GUI. Подготовленный нативный транспорт теперь находится в отдельных модулях; доступного аппаратного запуска нет. Ответы содержат `simulationOnly=true`, `hardwareControlAvailable=false`. Обычный daemon mode требует Apple-issued подпись и root; режим предназначен для launchd, но происхождение процесса отдельно не проверяет. Приём сообщений ограничен подписью клиента той же команды. Положительный installed сценарий пока не проверен. Локальная `security find-identity -v -p codesigning` снова дала **0 valid identities**. Подключение аппаратного recovery broker, локальной выдачи одобрения и installed проверка ещё нужны до готового плана сеанса владельца. Пароль и системное одобрение сейчас не запрашивались.

Подготовлен [неодобренный кандидатный план](evidence/candidate-experiment-plan.json), связанный с хешами собранных app/helper. Чистые тесты отвергают подмену бинарника, диапазона, команды, lease или readiness. Перечень содержит предполагаемые операции с `Ftst`, `F*Md`, `F*Tg` и условия каждой записи; аппаратный runtime не подключён. Типы взяты из локального read-only результата; роль ключей и сброс целей в Auto сопоставлены с [fan.rs](https://github.com/raminsharifi/MacFanControl/blob/main/src/fan.rs) и [control.rs](https://github.com/raminsharifi/MacFanControl/blob/main/src/control.rs). Наши пределы одной попытки и сроки — проектный выбор; успешность последовательности на macOS 27 **не подтверждена**. `readyForOwnerApproval=false`: этот экспорт не является готовым сеансом владельца, не принимает разрешение и не выполняет аппаратных операций.

Новый [протокол опыта](../features/feature-experiment-protocol.md) проверен без аппаратных записей: десять C-пакетов совпали с кандидатным планом, чужие/устаревшие решения отвергнуты, попытки сохраняются до I/O, replay остаётся запрещён после нового экземпляра и Auto. 39 тестов прошли (10 core, 17 control, 12 experiment). Нативный factory требует hardware domain, root, текущую загрузку, подпись/хеши и недекодируемое свидетельство recovery; последнее текущий worker не выдаёт. Positive native open/write не запускался. Встроенный dry-run инстанцирует только модель. Проверка `nm` собранных executable подтвердила writer в helper и отсутствие его open/write-symbols в GUI.

В настоящем anonymous XPC `prepareHardwareExperiment` вернул кандидата/блокеры; start с корректным digest и произвольным challenge UUID был отвергнут с `hardwareRuntimeNotPrepared`, некорректный формат — `invalidApprovalRequest`; симуляция затем прошла. `kern.bootsessionuuid` вернул корректный UUID вне песочницы Codex без sudo; внутри песочницы чтение было запрещено. Значение не публиковалось. Привязка к загрузке проверена модельными тестами; production issuer и живой аппаратный восстановитель ещё не проверены.

### Проверка надзора за самим writer — 2026-10-01

Добавлены `RecoveryMonitor`, private-pipe broker и отдельные Fixed/Auto-процессы для файловой модели. Проверяется тот же consumed ledger и точный набор десяти шагов. Broker сохраняет Fixed closure до сигнала своему writer; Auto разрешается только после подтверждённого завершения writer. Ответ на операцию ограничен 0,5 с, ожидание выхода — 1 с; эти сроки включены в candidate schema 2 и его digest. Начало Auto не продлевает уже сохранённый срок восстановления при ошибке writer. В authority устранено сохранение некорректной restoration epoch при обратном ходе clock.

Первый полный process dry-run прошёл: обычный Auto, SIGKILL/SIGSTOP helper и writer, зависание Fixed/Auto после сохранённого эффекта, частичный отказ fan zero, SIGTERM broker, injected sleep и абсолютный lease. При частичном отказе запрос fan one всё равно выполнен; небезопасные clear-target/release-unlock не выполнены, pending сохранён. При зависшем Auto попытка не повторена. Power callback теперь может отложить acknowledgement; в модели он следует после bounded recovery. [Протокол с точными сроками и бинарным хешем](evidence/recovery-dry-run.txt). 45 тестов прошли (10 core, 17 control, 18 experiment); docs_check: 11 документов, 30 BDD, без ошибок. Подписи ad hoc снова strict-verified; в keychain снова **0 valid identities**. [Общий протокол программных проверок](evidence/software-verification.txt).

Требование выхода процесса опирается на документированное значение [Apple `Process.isRunning`](https://developer.apple.com/documentation/foundation/process/isrunning): false после завершения или неудачного запуска; для наших children успешный `run()` и handshake проверяются отдельно. Это проверка прекращения процесса модели. **Отмена уже начатого kernel SMC I/O, SIGKILL самого broker, потеря питания и аппаратный Auto этим не установлены.** Новый путь создаёт только `FileSimulatedStepDevice`, работает non-root и не выдаёт `ArmedHardwareRecovery`. Аппаратная привязка broker, доверенный локальный issuer, положительная installed проверка и единый сеанс владельца ещё нужны; аппаратный старт остаётся закрыт.

### Общая связка broker и изолированных children — 2026-10-01

Владелец объединил PR #1 и #2; работа начата от `origin/main` (`534cf11`). В `ExperimentRecoveryBroker.swift` собран общий цикл для simulation/hardware domain: отдельные Fixed, Auto и read-only reader children, private-pipe handler для свежих recovery probes, closure и подтверждённый выход **writer** до Auto. `ScopedExperimentChild` связывает роль/phase/scope с consumed ledger; нативная ветка может создать witness только с аппаратным root ledger и live probe, а native factory по-прежнему требует подпись/boot/точные бинарники. Положительная аппаратная ветка не вызывалась. XPC start сохраняет отказ; локальный issuer и установленный helper ещё не готовы.

Из broker loop убраны синхронные device reads: отдельный reader возвращает только ограниченный `BrokerObservation`, привязанный к единственному outstanding ID, scope, PID, роли, deadline и timestamp запроса. Профиль/диапазоны/числа/pressure проверяются повторно при приёме. Read-only child не получает executor. Отказ reader в Fixed закрывает writer и инициирует Auto; отказ reader в Auto не отменяет оставшиеся допустимые Auto-попытки, но запрещает финальное подтверждение. Старый read-only child получает остановку; ожидание его IOKit не блокирует запуск восстановителя. Процессные дескрипторы происходят только из детей этого broker; внешних PID/путей в XPC не добавлено.

Финальная сборка прошла **71 unit-тест** (10 core, 17 control, 44 experiment) и **16 процессных сценариев**, включая ранний отказ Auto reader. Anonymous XPC/старый worker dry-run также прошёл; [протокол](evidence/recovery-dry-run.txt) связан с текущим SHA-256. Это подтверждает логику модели, а не SMC I/O или физический Auto. docs_check: 11 документов, 41 BDD, без ошибок.

Это read-only проверка, без native writer, sudo/установки или реального сна.

### Локальное одобрение и restart — 2026-10-01, работа после PR #3

Владелец объединил [PR #3](https://github.com/mdub1na/ventilator2/pull/3); новая ветка основана на main `cef07d9`. Прочитанный и скомпилированный код добавляет `LocalApprovalIssuer`, полный `LocalApprovalReview` и `BrokerRestartRecovery`. 82 unit-теста прошли, включая точное подтверждение/отказ/replay/подмену review и восстановление оставшихся Auto-шагов с исходным deadline. Положительный root/Apple-signed/installed путь пока не выполнялся.

Одобрение связывает candidate schema 3 и полный текст инструкций двумя SHA-256. Выбрано точное локальное подтверждение challenge + обоих digest вместо короткого yes: изменение текста сеанса должно отменять ранее показанное подтверждение. Hardware issuer требует root TTY, проверенные app/helper одной команды, профиль и `SMAppService.status == .enabled`. По [Apple](https://developer.apple.com/documentation/servicemanagement/smappservice/status-swift.enum/enabled), это регистрация и право запускаться; статус не доказывает работу процесса. Поэтому он остаётся предварительным installed gate, положительный установленный сценарий ещё нужен.

Решение restart: каждый device writer/restorer держит отдельный lifetime flock до закрытия соединения. Новый broker сначала закрывает Fixed в журнале, затем требует эту блокировку; сохранённых PID нет. При занятом устройстве Auto не начинается. После освобождения используются новый nonce, только ещё не зарезервированные Auto-шаги и исходный восьмисекундный срок. Возвращённые вызовы отмечаются отдельно от попыток; отсутствующий return у прежнего Auto не разрешает повтор и сохраняет pending. Это механизм контроля процессов, не доказательство отмены kernel I/O или физического Auto.

[TTY/restart dry-run](evidence/local-approval-restart-dry-run.txt) прошёл шесть групп проверки issuer и шесть restart-сценариев на текущем helper: полный review показан до ввода, approval не запускает устройство; SIGKILL в Fixed и частичном Auto продолжены без повторов; неизвестный Auto return, занятое устройство, исходный timeout и чужой boot сохраняют pending. Одобрение в этих процессных случаях получено через TTY и потреблено настоящим model begin, а не подставлено в JSON. Старые 16 recovery-сценариев и anonymous XPC/worker dry-run также прошли. Обновлённый helper повторно прочитал реальный SMC без root; [снимок](evidence/experiment-read-only.json). Нативный writer не открывался.

Наблюдение при разработке harness: на этом Mac остановленный SIGSTOP writer исчезал после SIGKILL его broker; такой случай не моделирует живое старое соединение или незавершённую kernel операцию. Для проверки отказа нового broker независимый non-root процесс удерживал device lock. Положительный отказ `deviceStillActive` и отсутствие новой epoch подтверждены этой файловой моделью; аппаратную отмену это не устанавливает.

### Signed/installed gate — 2026-10-01, продолжение после PR #4

PR #4 на старте этого шага открыт (`11f5bb0`); работа продолжается в отдельной ветке поверх него. Повторное read-only `security find-identity` подтвердило прежние две записи: первая явно revoked, вторая — кандидат без этой пометки. Приватный ключ не экспортировался, ACL/keychain не изменялись.

До возможного codesign проверен отдельный процесс `tools/sign_without_ui.swift`: публичный `SessionCreate` должен был создать security session без graphics/TTY, затем exec наследует её. SDK `Security/AuthSession.h` и [Apple SessionCreate](https://developer.apple.com/documentation/security/sessioncreate%28_%3A_%3A%29) подтверждают область одного процесса, наследование и потерю его прежних security rights. На текущем Mac API вернул `OSStatus=100001`; wrapper остановился **до exec codesign и обращения к приватному ключу**. Это отказ создания headless session, не доказательство неисправной identity. Бездиалоговая подпись не подтверждена; обычный codesign может потребовать участия владельца и будет включён в единый сеанс из задания, а не запущен вслепую.

Решение installed gate: отдельно проверять целостность/Apple-issued подписи и точный app/helper/LaunchDaemon layout, расположение `/Applications/Ventilator.app`, root ownership без group/other write, затем enabled регистрацию и живой XPC ответ. XPC обеих сторон получает requirement с Team ID и CDHash конкретного counterpart; ответ сверяется с audit-token UID/PID, nonce, digest бинарников/plist и сроком 2 с. Регистрация по [Apple](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29) требует административного одобрения для LaunchDaemon; поэтому такой positive сценарий пока не выполняется.

На текущей сборке прошли 91 unit-тест (9 новых installation policy/native-negative), [отказы установки](evidence/installation-dry-run.txt), anonymous XPC/worker, все 16 recovery и 6 TTY + 6 restart process-сценариев. Actual ad hoc app отказал register/unregister до изменения SMAppService; состояние осталось `notFound`. Подменённый launch layout и symlink отвергнуты настоящим inspector. Проверка требований использовала нативный Security parser; root peer/fingerprint/deadline/removal policies проверены на модели, не на установленном daemon. `codesign --verify --strict` прошёл для ad hoc app/helper; GUI по-прежнему без writer symbols. Hardened Runtime без debugger/injection/JIT exceptions обязателен для signed ветки; положительная подпись ещё не получена. Expiration/trust anchors проверяются offline с `noNetworkAccess`; online revocation/notarization этим gate не подтверждены.

Новая сборка получила [свежий read-only снимок](evidence/experiment-read-only.json) на Mac15,7 / 26A428: Ftst=0, modes=3/3, actual/target=0/0, прежние диапазоны, nominal pressure, чтение 0.002632 с. Открывался только CSMCRead. [Кандидат](evidence/candidate-experiment-plan.json) обновлён по проверенным бинарным хешам и остаётся readyForOwnerApproval=false. [Сводка](evidence/software-verification.txt) связывает результаты с этой сборкой. Подписанный installed positive, административное одобрение, настоящий сон и аппаратная запись не запускались; следующий кодовый шаг — hardware admission/runtime и полный единый сеанс владельца.

### Guarded runtime и остановленная транзакция — 2026-10-01

В main перенесено дерево PR #5 отдельным PR #6 (`87e125d`): исходный PR #5 был смержен в ветку PR #4. Теперь реализован [runtime опыта](../features/feature-owner-experiment-runtime.md): отдельный preflight-процесс до consuming begin, XPC owner binding, private broker, heartbeat/Auto/status и startup recovery оставшихся Auto. Аппаратная ветка требует installed identity, root, enabled service и локальный hardware receipt; положительный нативный путь ещё не выполнялся.

[Четыре модельные проверки runtime](evidence/session-runtime-dry-run.txt) прошли через реальные XPC/Process: явный Auto, invalidation связи, новый daemon при живом broker и после SIGKILL собственного model broker. Повторный Fixed/Auto не допускается, authority/receipt не заменяются. Диагностические status/heartbeat читают защищённые atomic snapshots без транзакционной блокировки, чтобы не мешать writer.

Полный recovery прогон выявил ранее скрытый race: SIGSTOP writer во время durable return удерживал `authority.lock`, и broker не мог сохранить закрытие Fixed. Реализован отдельный fsync-маркер отзыва, не использующий эту блокировку; Fixed проверяет его перед I/O. После подтверждённого выхода собственного writer broker обновляет основной ledger и начинает Auto. Unit-тест удерживает настоящий flock; процессный fault детерминированно останавливает модель внутри транзакции. Обе проверки и все **17 recovery-сценариев** прошли. Завершение процесса по-прежнему не считается доказательством отмены начатой kernel SMC-операции.

Итог: 92 unit-теста, четыре runtime, 6 TTY + 6 restart и прежние installation/control проверки; docs_check — 13 документов/61 BDD. [Сводка](evidence/software-verification.txt) связывает результаты с хешами. [Свежий read-only снимок](evidence/experiment-read-only.json): Ftst=0, modes=3/3, actual/target=0/0, nominal pressure, 0.003418 с. Только CSMCRead, без root/записи. Pending hardware сохраняется даже после кодов Auto, physicalAutoVerified=false. Следующий шаг — клиент владельца и полный единый сеанс подписания/установки/ограниченного опыта; продуктовый hardware control закрыт.

## Гипотезы и адреса проверки

### Предшествующее решение runtime шага — 2026-10-01

PR #5 был объединён в исходную ветку PR #4; отдельный PR #6 перенёс это дерево в main (`87e125d`). Проверено через Git ancestry, GitHub merge state и повторные 91 unit-тест/12 документов. Следующая **цель реализации** — единый клиент отдельного broker для daemon и модели: bound read-only preflight в отдельном процессе перед consuming begin, явный hardware start только при локальном receipt той же XPC-связи, startup recovery только оставшихся Auto-шагов. Одобрение выдаёт root TTY, а не XPC. Обычный GUI и признак пользовательского hardware control остаются закрытыми. Модель проверит этот же proxy/launch путь без выдачи hardware authority; положительный подписанный установленный сценарий войдёт в единый сеанс владельца.

## Риски и механизмы снижения

| Риск | Механизм и критерий |
|---|---|
| Фиксированный режим может пережить аварию контролирующего процесса. | До записи сохранять durable marker «требуется Auto»; при старте помощник восстанавливает Auto. Для опыта предусмотреть независимый ограниченный по времени восстановитель и готовую команду владельца. Проверять реальный возврат после аварии. `launchd`-перезапуск сам по себе не является доказательством безопасности при `SIGKILL`, потере питания или отказе демона. |
| `Ftst` может временно изменить взаимодействие с системным thermal manager. | Если выяснится, что он необходим, включить его в **полный список аппаратных записей** в плане владельца, вместе с обратной записью и порядком. Остановиться при любом расхождении чтений; не повторять неудачный опыт. |
| Ложная температура способна сделать последующую кривую опасной. | Граница правдоподобия, тип и возраст данных, раздельное состояние ошибки; при потере валидного датчика инициировать Auto. Кривую проектировать только после фиксированного режима и проверенных температур. |
| Системный thermal manager может отвергнуть запись или позже отобрать управление. | Считать отказом расхождение режима, цели и фактических RPM после ограниченного ожидания; не выдавать UI «ручной режим» до независимых чтений. Не пытаться бесконечно повторять запись. |
| Потеря соединения XPC при закрытом окне оставит состояние неясным. | Помощник не привязан к окну; heartbeat/lease, по истечении которого он инициирует Auto. UI показывает потерю связи; проверка на реальном Mac в M2. |
| Обновление или удаление может оставить helper активным. | В M3 проверить unregister, процесс, state и Auto до и после обновления/удаления; тестировать из установленного app bundle, а не только из Xcode. |

## Следующие этапы и условия перехода

1. **M1 — наблюдение:** проект, read-only SMC/HID, честные `unknown` для CPU/GPU, окно и значок созданы. На текущем Mac без записи подтверждены два вентилятора, `0 RPM`, NAND-канал SSD, четыре раздела и работа процесса после закрытия окна. Владелец подтвердил значок на живом экране. Температурные кандидаты проверены короткими нагрузками; CPU/GPU остались неатрибутированными.
2. **M2 — подготовка ограниченного опыта:** реализовать закрытый helper/XPC, предохранители, mock-тесты, dry-run, восстановление, подпись и проверку установленного bundle. Составить **один** план сеанса владельца с командами, системными окнами, длительностью, условиями остановки, SHA-256 бинарника и исчерпывающим перечнем SMC-записей. Только затем запросить одно явное одобрение конкретного опыта.
3. **M2 — аппаратная проверка:** после одобрения выполнить один опыт с умеренной целью внутри считанного диапазона и коротким сроком; подтвердить цель, режим, изменение actual RPM, работу при скрытом окне и устойчивый Auto. При неуспехе оставить управление отключённым.
4. **M3 — поставка:** только после успешной проверки подключить управление в UI; испытать установку, login item, сон/пробуждение, аварии, обновление и удаление. Другие модели рассматривать отдельно.

На 2026-09-30: **проверено на оборудовании** — чтение двух вентиляторов, NAND-канала SSD, окно и продолжение процесса после закрытия; значок подтверждён владельцем, экран температур проверен по скриншоту. **Проверено симуляцией** — preflight, lease/heartbeat, ошибки показаний/профиля/диапазонов, подставной sleep/disconnect, журнал после SIGKILL, три чтения Auto-кода, отдельный worker при SIGKILL/SIGSTOP помощника и отказ восстановления; **проверено локальным непривилегированным XPC** — обмен и binding соединения. Также проверены регистрация power observer и целостность кандидатного плана. **Не доказано** — CPU/GPU-атрибуция, запись, независимое управление, физический возврат Auto, аппаратная безопасность сна/аварии, положительная подпись/установка/auth helper и независимое восстановление оборудования.
